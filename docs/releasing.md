# Releasing Thermals

Thermals ships as a Homebrew cask from the public tap [`radkode/homebrew-thermals`](https://github.com/radkode/homebrew-thermals), which hosts the signed release zips so this repo can stay private. Users install with `brew install --cask radkode/thermals/thermals` and update with `brew upgrade --cask thermals`.

## Cutting a release

1. Bump `MARKETING_VERSION` and `CURRENT_PROJECT_VERSION` in `project.yml`, commit, and push to `main`. Sparkle offers an update only when the build number goes up.
2. `.github/workflows/release.yml` runs on any push that touches `project.yml`. Its `check` job skips versions that already have a `v<version>` tag. Otherwise the `release` job runs `scripts/release.sh --ci` on a `macos-26` runner: Release build, Developer ID signing with hardened runtime, notarization and stapling, then the zip and appcast are signed for Sparkle, both go up as a release in the tap, `Casks/thermals.rb` is rewritten there, and `v<version>` is tagged here.
3. Verify:
   - `gh run list -R radkode/thermals --workflow release.yml --limit 3`
   - `gh release list -R radkode/homebrew-thermals`
   - `brew update && brew upgrade --cask radkode/thermals/thermals`, then `spctl --assess --type execute -vv /Applications/Thermals.app` must print `source=Notarized Developer ID`.

On an already tagged version, `gh workflow run release.yml -R radkode/thermals --ref main` runs a secret-free build and test preflight on the release runner. On an untagged version, the same command starts a release, so check the current version and tag first.

Don't:
- hand-edit the tap's `Casks/thermals.rb`;
- create `v*` tags by hand (a tag makes the workflow skip that version);
- run `scripts/release.sh` without `--dry-run` from an agent session.

`scripts/release.sh --dry-run` builds, ad-hoc signs and writes the cask to `build/release/<version>/` without notarizing or publishing.

The cask's `uninstall quit:` makes `brew upgrade` quit a running Thermals and reopen the new build. Without it the old process keeps running from a replaced bundle, and `SMAppService` refuses every register and unregister (`Register (<private>) error: 1` in the unified log), so LAUNCH AT LOGIN silently does nothing. To see those errors, use `/usr/bin/log show`, because zsh's builtin `log` shadows it.

## Toolchain gap

CI builds with the default Xcode on the `macos-26` image (printed at the top of the build step), which is older than the Xcode used locally (27.x). The workflow pins `actions/checkout` to a commit and verifies the SHA-256 of XcodeGen 2.46.0 before running it. Review both pins when updating those tools. Code that compiles locally can fail only in CI. The first 0.1.0 run on `macos-15` (Xcode 16.4) timed out type-checking one long expression in `PreviewMonitors.swift`. Long literal-heavy expressions should be split into typed `let`s.

## Credentials

The workflow's secrets live on `radkode/thermals`; the originals belong in the private credential store. To rotate any of them, run `scripts/set-release-secrets.sh <DeveloperID.p12> <AuthKey_KEYID.p8>` in a terminal. It checks the `.p12` password and the notary key with Apple before setting anything.

| Secrets | What | Expires |
|---|---|---|
| `DEVELOPER_ID_CERT_P12_BASE64`, `DEVELOPER_ID_CERT_PASSWORD` | Developer ID Application certificate and its export password. Keep ownership and expiry records in the private credential store. | Check private inventory |
| `NOTARY_KEY_P8_BASE64`, `NOTARY_KEY_ID`, `NOTARY_KEY_ISSUER` | App Store Connect notarization key and identifiers. | Until revoked |
| `TAP_TOKEN` | Fine-grained token `thermals-release`, owner `radkode`, Contents read and write on `radkode/homebrew-thermals` only. | No expiration |
| `KEYCHAIN_PASSWORD` | Random throwaway for the runner's temporary keychain; generated by the helper. | n/a |

Automatic releases from `main` are an explicit choice. This private GitHub Team repository cannot require an environment reviewer, so anyone who can change `main` can change the release job that receives signing and publishing secrets. Restrict `main` write access and treat account security as the release approval boundary. SHA-pinned actions and a verified XcodeGen archive limit upstream changes, but they do not protect against a compromised `main` writer. See [issue #9](https://github.com/radkode/thermals/issues/9) for the remaining risk.

## Gotchas we hit setting this up

- **Xcode's "Developer ID Application" option was greyed out** for the account holder. Workaround: generate a CSR with Certificate Assistant, then create the certificate at developer.apple.com › Certificates › + › Developer ID Application (G2 Sub-CA) and double-click the downloaded `.cer`. On macOS 27, Keychain Access no longer has the Certificate Assistant menu; the app is at `/System/Library/CoreServices/Certificate Assistant.app`.
- **Keychain Access exports `.p12` files with legacy RC2-40 encryption.** OpenSSL 3 and later read them only with `-legacy`; the helper falls back to it. macOS `security import` (used in CI) reads them fine.
- **HTTP 401 from the tap** means `TAP_TOKEN` is invalid (in our case a token pasted twice). `scripts/release.sh` now checks write access to the tap before building. A fine-grained token is shown only once; regenerate it if lost.

## In-app updates (Sparkle)

The app reads `https://github.com/radkode/homebrew-thermals/releases/latest/download/appcast.xml` (`SUFeedURL` in `project.yml`), requires a signed feed (`SURequireSignedFeed`), and only installs a zip whose EdDSA signature matches `SUPublicEDKey`. Both signatures come from the private key in the login keychain under the Sparkle account `thermals`, and in CI from the `SPARKLE_ED_PRIVATE_KEY` secret. Keep its backup and recovery instructions in the private credential store (`generate_keys --account thermals -f <file>` restores it to a keychain). Losing it means shipped copies can't be updated in-app. To set or rotate the secret from the keychain (resolve packages first so `build/SourcePackages` exists; `generate_keys -x` refuses a path that already exists, so it writes into a fresh directory):

```bash
(D="$(mktemp -d)"; trap 'rm -rf "$D"' EXIT
  build/SourcePackages/artifacts/sparkle/Sparkle/bin/generate_keys --account thermals -x "$D/key" \
    && gh secret set SPARKLE_ED_PRIVATE_KEY -R radkode/thermals < "$D/key")
```

The release script refuses to publish when `CURRENT_PROJECT_VERSION` isn't above the last tag's, or when the zip's signature doesn't verify against the app's `SUPublicEDKey` (checked with Homebrew's `openssl@3`; the system LibreSSL can't verify Ed25519). It re-signs Sparkle's nested code (XPC services, Autoupdate, Updater.app, the framework) inside out with the Developer ID before signing the app, because notarization rejects the ad-hoc signatures Xcode leaves on them.

To test an update end to end without releasing, build the release script's dry-run app twice, set `SUFeedURL` in both copies to `http://127.0.0.1:<port>/appcast.xml`, give the second a higher `CFBundleVersion`, re-sign both with the Developer ID, then zip the second, sign it with `sign_update --account thermals` and serve it with a one-item appcast. Set `SUHasLaunchedBefore` true and `SULastCheckTime` in the past in `com.radkode.thermals` defaults so the first copy checks at launch, then delete those keys and `updateNotifiedVersion` afterwards. A Thermals process is a menu bar app, so `Updater.install` activates it first, otherwise Sparkle's window opens behind other apps.

The cask does not declare `auto_updates true` yet. Brew judges that flag from the tap's current cask, so adding it in the first Sparkle release would stop `brew upgrade` from moving 0.2.0 installs onto a version that can update itself.
